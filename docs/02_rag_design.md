# RAG 파이프라인 설계문서 — Can I run this model?

## 1. 전체 흐름

```
[사용자 질문 + 선택 모델]
   │
   ├─ (질문 시점 수집) collector.collect ─────────────────────────────────────────────┐
   │    1. 프롬프트 1: 검색어 추출 (JSON 배열)                                          │
   │    2. 검색어 라우팅: 저장소형(모델 ID·GGUF) → HF 저장소 검색 / 개념어 → 위키백과    │
   │       + 모델 카드가 연결한 arXiv 논문(태그 arxiv:<ID>)                             │
   │    3. 코드 필터: 같은 모델의 변형 저장소만 (다른 모델 카드 제외)                     │
   │    4. 프롬프트 2: 제목·요약만 보고 선별 (JSON)                                      │
   │    5. 본문 수집 (+ 강제 포함: 선택 모델의 모델 카드, 라이선스 질문이면 LICENSE 원문) │
   │    6. 청킹·임베딩 → model_docs upsert, 수집 캐시 기록                              │
   │                                                                                  │
   └─ LangGraph ── retrieve ──────────────► generate ─────────────► [답변 + 인용 근거] ◄┘
                  · [근거 1] = model_meta     · 프롬프트 3 (근거·계산값만 사용)
                  · model_docs (모델 필터)    · 계산값 출처·라이선스 면책을 코드로 보장
                  · 라이선스 원문 (질문 시)   · [근거 n] 파싱 → 인용된 근거만
                  · 개념 문서 (개념 검색어)   · 근거 수치 검증 → 경고
                  · 병합·중복 제거·번호 부여
[하드웨어 판정·속도(계산값)] ───────────────────┘ (calc 블록으로 생성에 전달)
```

- 그래프: `python -m app.rag.graph` → 노드 `retrieve`, `generate`, 엣지 `__start__ → retrieve → generate → __end__`
- 질문 1건 처리 진입점: `app/rag/pipeline.ask()` (수집 → 그래프 스트림 실행, 단계 콜백, 예외 → 사용자 문구)

## 2. 컬렉션 구성 (Chroma, 코사인 거리)

| 컬렉션 | 내용 | 청크 단위 | 청크 ID | 현재 청크 수 |
|---|---|---|---|---|
| `model_meta` | 모델 메타데이터 항목 텍스트 | 항목당 1청크 | 모델 ID (`Qwen/Qwen3-8B`) | 150 |
| `model_docs` | 외부 문서 | 출처별 청킹 | `모델ID:문서ID:순번` (`Qwen/Qwen3-8B:hf_card:Qwen/Qwen3-8B-GGUF:2`) | 727 (arXiv 438, HF 카드 220, 위키 37, 라이선스 32) |

메타데이터와 외부 문서를 분리한 이유: 메타데이터는 검색 없이 선택 모델의 1건을 항상 [근거 1]로 넣고(F2006), 조건 탐색(F2011)은
메타데이터만 검색한다. 한 컬렉션에 섞으면 조건 탐색 결과에 문서 청크가 섞이고, 근거 수 조절(Top-k)에 메타데이터가 끼어든다.

### 청크 메타데이터

| 컬렉션 | 필드 |
|---|---|
| `model_meta` | `model_id`, `doc_title`, `source_url`(HF 모델 페이지), `source_type`=`model_meta`, `org`, `params`, `license`, `languages`, `gated` |
| `model_docs` | `doc_title`, `source_url`, `source_type`(`hf_card`·`hf_license`·`wikipedia`·`arxiv_pdf`), `page`(PDF), `doc_id`, `model_id`(관련 모델), `query`(찾은 검색어), `collected_at`, `content_hash` |

- `model_id`는 검색 범위를 선택 모델로 좁히는 필터다. 빠지면 다른 모델의 문서가 근거에 섞인다.
- 청크 ID에 모델 ID를 넣어, 여러 모델이 같은 문서(예: 위키 "컨텍스트 윈도")를 수집해도 서로 덮어쓰지 않는다.
  같은 본문이 여러 모델 ID로 들어가는 중복은 검색 단계에서 `content_hash`로 제거한다.

### 항목 텍스트 설계 (`item_text.py`)
`모델명 · 제작사 · 파라미터 수 · 아키텍처(MoE 전문가 수) · 레이어/KV 헤드 · 컨텍스트 · 라이선스 · 라이선스 원문 · 지원 언어 · 기반 모델 · 태그(용도)`
- 용도·언어를 넣은 이유: "한국어 되는 코딩용" 같은 조건 탐색이 걸리게 하기 위해서.
- 언어는 코드(`ko`)만 있으면 한국어 질의에 안 걸려 `한국어(ko)`로 풀어 쓴다.
- 값이 없는 언어·태그 줄은 넣지 않는다. "지원 언어: 정보 없음" 줄이 오히려 "한국어 지원" 질의에 걸렸다.

## 3. 수집 → 청킹 → 색인 순서

1. **메타데이터 (오프라인 준비)**: HF Hub 목록(다운로드순) → 양자화 파생·테스트용·safetensors 없는 저장소 제외 → 각 모델 `config.json` → `models.json` → 항목 텍스트 임베딩 → `model_meta`
2. **외부 문서 (질문 시점)**
   1. 프롬프트 1 검색어 추출 → 정규화해 캐시에 없는 검색어만 수집 (NF2002)
   2. 라우팅: 모델명·모델 ID·양자화 형식이 들어간 검색어는 HF 저장소 검색, 나머지는 위키백과 (한국어 우선, 없으면 영어)
   3. arXiv: 모델 HF 태그의 `arxiv:<ID>` 논문 (첫 수집이거나 학습·벤치마크·구조 질문일 때)
   4. 코드 필터 `same_model_repo`: HF 후보는 "모델명 + 양자화 표기" 저장소만 남긴다
   5. 프롬프트 2 선별 → 본문 수집. 강제 포함(선택 모델의 모델 카드, 라이선스 질문이면 LICENSE)은 선별·길이 제한과 무관
   6. 원문을 `data/cache/docs/`에 저장(다른 모델이 같은 문서를 고르면 재사용) → 청킹 → 같은 (모델, 문서)의 기존 청크 삭제 후 upsert
   7. 색인까지 끝난 뒤에만 캐시에 기록 (중간 실패 시 다음 질문에서 재시도)

## 4. 청킹 전략

기본 **1000자 / 중복 200자** (`config.yaml chunking`). `RecursiveCharacterTextSplitter`.

| 출처 | 방식 | 이유 |
|---|---|---|
| HF 모델 카드 | 마크다운 헤더(#, ##, ###)로 먼저 나눈 뒤 크기 분할, 청크 앞에 `[헤더 경로]` | 카드는 "Quickstart", "Best Practices", "License"처럼 절마다 주제가 분명하다. 절 경계를 지키면 한 청크에 서로 다른 주제가 섞이지 않고, 헤더 경로가 남아 검색이 잘 걸린다 |
| arXiv PDF | 쪽 단위로 나눈 뒤 크기 분할 | 근거에 쪽 번호를 표시해야 해서 청크가 쪽 경계를 넘지 않게 한다 |
| 위키백과 | 크기 분할만, 수식 덩어리 제거 | 평문. `explaintext`가 수식(MathML)을 한 글자씩 줄바꿈해 내보내 쓰레기 청크가 생겼다 → 4줄 이상 이어지면 `[수식]`으로 치환 (트랜스포머 문서 51,104자 → 24,589자) |
| 라이선스 원문 | 크기 분할만 | 평문 |

- **1000/200을 고른 이유**: 모델 카드의 절 하나가 한 청크에 담기게 하려는 것이다. 예를 들어 Qwen3-8B-GGUF 카드의 샘플링 권장값(thinking/non-thinking 모드의 Temperature·TopP·TopK·MinP·PresencePenalty)은 한 청크에 모두 들어 있었다. 중복 200자는 절 경계에 걸친 문장이 양쪽 청크에 남게 한다.
- **바꿨을 때의 차이** (`scripts/reindex_docs.py`, Qwen3-8B 문서 3건): 1000/200 → 청크 42개, **500/100 → 70개**. 같은 top_k=5라면 근거로 들어가는 본문 양이 약 절반으로 줄어든다. 500자일 때의 답변 품질은 따로 비교하지 않았고, 1000을 유지했다.

## 5. 프롬프트 (`app/rag/prompts.py`)

| 프롬프트 | 역할 | 입력 | 출력 형식 | 실패 처리 |
|---|---|---|---|---|
| **1. 검색어 추출** | 로컬 LLM 배포 전문가 | 선택 모델 항목 텍스트 + 질문 | JSON 문자열 배열 (≤5개) | JSON이 아니면 형식을 다시 요구하며 1회 재요청 → 그래도 실패하면 `[모델 ID]` |
| **2. 후보 선별** | 로컬 LLM 배포 전문가 + 자료 조사 담당 | 질문, 모델 ID, 후보(id/출처/제목/요약 200자) | `{"selected": [후보 id], "reason": "..."}` | 1회 재요청 → 실패 시 검색어별 첫 후보. 목록에 없는 id는 버림 |
| **3. 답변 생성** | 로컬 LLM 배포 전문가 | 근거(`[근거 n] (출처 유형) 제목` + 본문), 계산값, 질문 | 한국어 답변, 주장·목록 항목마다 `[근거 n]` | 근거 없으면 "제공된 문서에서 확인되지 않습니다" |

핵심 규칙
- 프롬프트 1: 검색어 형태로 출처가 정해진다는 것을 알려 준다(저장소형 vs 개념어). 개념 검색어는 개념의 뜻·원리를 물을 때만, 하드웨어 이름은 검색어로 쓰지 않음(사양은 표로 계산), "양자화"처럼 다른 분야와 겹치는 말 피하기. 예시 3개.
- 프롬프트 2: 고를 것(같은 모델의 양자화 저장소, 공식 저장소 우선, 같은 분야의 위키, 기술 보고서) / 버릴 것(세대·크기·종류가 다른 모델, 공식 카드를 반복하는 변형, 동음이의 문서). 확신이 없으면 고르지 않음.
- 프롬프트 3: 근거·계산값만 사용, 수치에는 반드시 근거 번호, 계산값은 "(계산값)" 표시, 근거끼리 다르면 둘 다 제시, 라이선스 조건은 원문 근거에 적힌 것만. 질문 바로 뒤에 `(형식: 문장과 목록 항목마다 끝에 [근거 n])`를 한 번 더 둔다(작은 모델이 마지막 지시를 더 잘 따름).
- 조건 탐색(F2011)은 별도 2단계 프롬프트: 조건 해석(JSON: query, languages, uses ∈ {code, math, reasoning, chat, vision, tool-use}, 파라미터 범위, must_fit_gpu) → 후보 메타데이터에서 선별(JSON: id, reason, 메타데이터 인용 evidence).

코드로 보장하는 것 (프롬프트만으로는 지켜지지 않았던 것)
- 선택 모델의 모델 카드(·라이선스 원문) 강제 수집, 다른 모델 저장소 제외 필터
- 계산값을 썼는데 [근거 1]을 밝히지 않으면 출처 문장을 덧붙임
- 라이선스 질문이면 면책 문구 덧붙임
- 인용 근거의 수치 검증 경고, 조건 탐색의 인용 근거 검증

## 6. 검색 설정 (`config.yaml retrieval`)

| 값 | 설정 | 선정 이유 |
|---|---|---|
| 메타데이터 | 1건 고정 ([근거 1]) | 판정·사양 질문의 기본 근거 |
| `top_k` | 5 | 모델 카드 질문은 대개 1~3개 청크에 답이 있다. 5면 공식 카드와 GGUF 카드, 기술 보고서가 함께 들어올 여유가 있고, 프롬프트가 지나치게 길어지지 않는다 (응답 약 4초) |
| `concept_top_k` | 2 | 개념 문서는 보조 설명. 프롬프트 1이 개념 검색어를 뽑았을 때만 그 검색어로 검색 |
| `license_top_k` | 3 | 라이선스 질문이면 원문 청크를 따로. 한국어 질문("상업적으로 써도 돼?")과 영어 원문은 임베딩 거리가 멀어 일반 검색에 안 걸렸다 |
| `search_type` | **mmr** (fetch_k 30, λ 0.5) | 아래 비교 결과 |
| `overfetch` / `near_dup_threshold` | 3 / 0.8 | similarity일 때 top_k×3개를 가져와 단어 3-gram 자카드 0.8 이상인 근사 중복을 지운 뒤 top_k를 채운다 |

**Top-k를 바꿨을 때** (질문 "thinking 모드 끄는 법과 권장 샘플링 설정은?", similarity):
- top_k=2: 근거 5개 → thinking 모드 방법만 답하고 "샘플링 설정은 확인되지 않습니다"
- top_k=8: 근거 11개 → [근거 8]에서 Temperature 0.6, TopP 0.95, TopK 20, MinP 0 등을 찾아 답함 (청크 본문에 해당 값이 있는 것을 확인)

**similarity vs MMR** (`docs/eval/mmr_comparison.md`, top_k=8, 근거 간 평균 코사인 유사도 — 낮을수록 덜 겹침)

| 질문 | similarity | similarity + 근사 중복 제거 | MMR |
|---|---|---|---|
| 구조(레이어, 헤드)와 컨텍스트 길이 | 0.729 (문서 3종) | 0.769 (2종) | **0.540 (4종)** |
| 사전 학습 데이터 | 0.723 | 0.726 | **0.607** |
| 권장 샘플링 설정 | 0.571 | 0.571 | **0.531** |
| 긴 텍스트 설정 | 0.480 | 0.480 | **0.374** |

기본값을 MMR로 한 결정적 이유: 기술 보고서 PDF 청크(438개)가 들어오자 similarity(top_k=5)는 공식 카드의 샘플링 청크를 놓쳤고,
한 번은 근거에 없는 "Top-k 50, Repetition Penalty 1.2 [근거 3]"을 지어냈다(다른 실행에서는 "확인되지 않습니다"). MMR은 같은 설정에서 공식 값을 찾았다.

## 7. 병합과 중복 제거 (`retrieve.py`)

1. `[근거 1]` 메타데이터 (검색 없음)
2. (라이선스 질문) 라이선스 원문 `license_top_k`개
3. `model_docs` where `model_id = 선택 모델`, `top_k`개
4. (개념 검색어가 있으면) where `source_type = wikipedia`, 모델 필터 없이 검색어마다 검색 → 거리순 병합 → `concept_top_k`개
5. 각 단계에서 `_Deduper`가 같은 청크 ID, 같은 `content_hash`, 단어 3-gram 자카드 ≥ 0.8(헤더 경로 줄 제외)을 버린다.
   공식 카드를 그대로 옮긴 GGUF 카드의 "Model Overview"처럼 헤더만 다른 청크가 근거 자리를 차지하지 않는다.
6. 순서대로 번호를 매기고 출처 유형 라벨: `[근거 1] (모델 메타데이터)`, `(HF 모델 카드)`, `(라이선스 원문)`, `(위키백과)`, `(arXiv PDF p.3)`

## 8. 근거 표시 방식 (`citations.py`, UI)

- 답변의 `[근거 3]`, `[근거 1, 3]`, `[근거1·3]`을 파싱해 **실제 인용된 근거만** 번호순으로 `[근거 n] 제목 · 출처 유형 · 원문` 링크로 표시. PDF는 `#page=N`으로 해당 쪽이 열린다.
- 근거 목록에 없는 번호(지어낸 인용)는 버린다. 인용이 하나도 없으면 "이 답변에는 인용된 근거가 없습니다."
- **수치 검증**: `[근거 n]`이 붙은 줄의 독립된 수치("0.6", "40,960", "36조")가 그 근거 본문(계산값 줄이면 계산값)에 있는지 검사해, 없으면 "인용한 근거에서 확인되지 않은 수치가 있습니다" 경고. 목록 번호, 모델명 속 숫자("Qwen3-8B")는 제외. 문맥까지 보는 검증은 아니다.
- 판정 카드: 파라미터 수·레이어·KV 헤드는 **[근거 1] (모델 메타데이터)** + 원문 링크, 대역폭은 **하드웨어 사양표** + 출처 링크, 공식은 **계산값**으로 구분.

## 9. 도메인 특화 기능 설계 이유 (F2010)

"내 PC에서 돌아가나"는 문서 검색만으로는 답할 수 없다. 모델 카드에는 모델 사양만 있고 사용자 하드웨어는 없다.
그래서 **근거(사양)는 메타데이터·문서에서, 계산은 코드로** 나눴다. LLM이 메모리를 계산하게 하면 F2015 비교처럼 FP16으로 잘못 계산한다.

| 기능 | 근거로 쓰는 것 | 계산 |
|---|---|---|
| 하드웨어 감지 | PC에서 직접 읽음 (pynvml, sysctl) + 사양표(대역폭, 공식 출처 URL) | — |
| 실행 가능 판정 | [근거 1] 파라미터 수·레이어 수·KV 헤드·헤드 차원 | 가중치(파라미터 × bpw ÷ 8) + KV 캐시(2 × 레이어 × KV 헤드 × 헤드 차원 × 컨텍스트 × 2바이트) + 오버헤드 10% |
| 속도 추정 | 사양표 메모리 대역폭, 모델명의 활성 파라미터 표기(MoE `A3B`) | 대역폭 × 효율 0.6 ÷ 토큰당 읽는 가중치. 오프로딩은 GPU·RAM 분담 시간 합 |
| 라이선스 안내 | LICENSE 원문 | — (면책 안내) |
| 조건 탐색 | 메타데이터 언어·파라미터·태그 | 하드웨어 판정을 카드에 붙임 |

- 양자화 bpw: Q6_K 6.5625, Q8_0 8.5는 llama.cpp `ggml-common.h`의 블록 구조 정의. Q4_K_M·Q5_K_M은 혼합 방식이라 구조값(4.5, 5.5)보다 커서 공식 Qwen3 GGUF 4종의 실제 파일 크기로 측정한 최댓값(4.97, 5.75)을 쓴다(보수적 판정). 같은 측정에서 Q6_K·Q8_0이 구조값과 일치해 측정 방법을 검증했다.
- 검산: Qwen3-8B, RTX 3080(10GB), 컨텍스트 4096 → Q4_K_M 가중치 4.74 + KV 0.56 + 오버헤드 = 5.8GB, 760GB/s × 0.6 ÷ 5.09GB ≈ 89.6 tok/s. 컨텍스트 32k면 KV 4.5GB로 모든 양자화가 "오프로딩 필요".
- 가정값(효율 0.6, 오버헤드 10%, RAM 중 모델용 0.8, Apple GPU 메모리 비율 0.7, 시스템 RAM 대역폭 51.2GB/s)은 `config.yaml`에 표시했고 실측으로 보정해야 한다.

## 11. 한계와 개선 방향

- 판정·속도는 추정치. 실측(llama.cpp `llama-bench`) 값으로 효율 계수를 보정해야 한다.
- RTX 40 시리즈 대부분과 Apple M1의 대역폭이 `TODO`(공식 출처 미확인)라 속도를 추정하지 않는다.
- 결론 문장("상업적 사용 가능")은 권리 부여 조항 청크가 상위에 들지 않으면 인용이 비기도 한다.
- 수치 검증은 수치 포함 여부만 본다(문맥 검증 아님).
- 언어 조건은 메타데이터 표기에 의존한다(Qwen3는 기술 보고서상 119개 언어를 지원하지만 카드 메타데이터에 표기가 없어 제외됨).
